Proof Before Done

A local browser application that checks a narrowly defined claim against a chosen file, then records a separate human decision. CHECK PASSED is not human acceptance.

Source snapshot: 01aa063 (verified implementation checkpoint). This map describes that snapshot; later code changes may require updates. This is technical documentation, not a record of a learner completing a code tour.

Main pieces

index.html and styles.css render the dashboard. src/app.js connects buttons and fields to the real checks and decisions. src/checks.js reads a selected local file, evaluates one criterion and attempts SHA-256. src/state.js invalidates outdated results. src/review.js requires a separate explicit decision. src/receipts.js produces JSON/Markdown records. tools/serve.mjs serves allowlisted assets on loopback.

Evidence is processed in the browser session. No persistent database, external API, account, or upload is part of the application. Exports are local unsigned records.

One action, end to end

A passing check is limited to the chosen criterion. Human review remains independent. A generated receipt is not a cryptographic signature or proof of overall project completion.

Three-stop reference route

  1. Input and result UI: src/app.js, search for $("run").onclick and invalidate(). The click handler passes claim, file, check type and criterion into a new run; input changes clear stale outcomes.
  2. Verified evidence: src/checks.js, find export async function check. This function enforces the 5 MiB limit, reads exact bytes, attempts SHA-256, and returns PASSED, FAILED or NOT VERIFIED for filename/text criteria.
  3. Decision and export: src/review.js, find recordReview, then src/receipts.js, find receipt, json and markdown. Confirmation and reviewer ID are required; exports keep machine and human outcomes distinct.

Activity status: This is a reference route based on actual source, not a claim that the owner manually toured or edited these files.

To change this, start here

  • Dashboard labels, forms or help text: index.html; appearance and responsive layout: styles.css.
  • Permitted evidence checks or limits: src/checks.js and regression coverage in tests/core.test.mjs. Changes to approved checks may require owner review.
  • Reviewer confirmation and exception logic: src/review.js, paired with src/app.js and tests.
  • Download fields and rendering: src/receipts.js; browser downloads are exercised in tests/browser.mjs.

A practice to reuse

The approved requirement “a passed check must not automatically accept a deliverable” is observable because src/checks.js produces an automated outcome, whereas src/review.js separately requires confirmed human review. devpost/verification.md records independent positive, negative, exception and invalidation tests, including 11 Node tests and 11 Edge browser checks.

Reusable method: state the exact result to prove, map it to a specific action and evidence, test a failing case as well as a passing one, and keep human acceptance independent of automated results. This preserves the X13 reverse-loop method without inferring anything the learner personally practiced.

Open the application again

From the project root, double-click start.cmd on Windows, or run node tools/serve.mjs with Node.js 24 or newer. Open the localhost address printed by the launcher. The application runs without Codex, cloud accounts, credentials or installing its dev dependencies.

Try the synthetic fixture fixtures/deliverable.txt. Text criterion WRONG fails; Delivery ready passes. A pass does not make a human decision. The selected file is limited to 5 MiB, supported text extensions are .txt/.md/.csv/.json, and PDF/image-content checks are not supported.
