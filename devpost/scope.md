# Proof Before Done | New Competition Proof of Concept

One line: an offline-first evidence checker that refuses to accept an AI worker's "done" claim without an observable check and a human decision.

## The Unique Kernel

The difference between an AI saying it completed work and **proof of one concrete result**. A check can pass without the whole job being accepted. Unproved claims remain NOT VERIFIED; evidence can fail; final acceptance remains with the human reviewer.

## Who It's For

The owner of a small company or an AI-assisted project who receives generated files and must decide whether a worker actually delivered a requested output, instead of trusting "done" messages.

## The Core Loop

The reviewer takes one worker completion claim, identifies one specific result that would prove a part of it, provides a sample evidence artifact, runs an observable check and receives a receipt showing what was tested and what actually happened. If it fails, the worker fixes the deliverable and the reviewer checks again. Repeat until a human accepts it.

## Inspiration & Identity

Based on the owner's X13 "Proof Before Done" principle and reverse Loop Generator planning method: start with the exact desired final proof, work backward to determine verifiable prerequisites, then build forward and test repeatedly. The prior prototype is **research and proof of feasibility only**; no code is to be copied into this new contest project. Expected character: practical, clear PASS / FAIL / NOT VERIFIED, not fictional AI certainty.

## Why This Matters to the Learner

The owner found a real release-process failure while preparing contest apps: working demos were incorrectly treated as submission-ready without checking the official Skill Pack requirement. They want a repeatable verification habit that stops incomplete work from being marked finished. They also want an eligible contest entry with honest evidence and a chance at prize money.

## What "Working" Looks Like

In a short browser demonstration the reviewer enters one claim, chooses a synthetic local evidence file and a checkable criterion, runs the check, and sees a grounded result plus a usable receipt. A wrong or missing file must never receive a false pass. A passing criterion does not turn the entire project into "accepted."

## The POC Boundary

**Now:** one locally selected test artifact, one objective exact check, a clear outcome, a human review gate and exportable receipt. A new implementation, written from scratch only after approved planning. No logins or paid APIs are required.

## Later

A broader multi-artifact release checker; dependency-aware verification across tests and submission gates; optional project agent integration; automatic comparison to build histories and public repository receipts.

## Explicitly Cut

- Automatic certification that an entire app or contest entry is eligible, because one selected-file criterion cannot establish that.
- Autonomous access to all local files or arbitrary execution, because it expands risk and scope.
- Cloud accounts, hosting, AI model integration or paid services, because they are unnecessary to prove the core loop.
- Copying old Proof Before Done source, because the new competition project must be newly implemented.
